94 — Token Cost Allocation Tracking

Attribute inference usage to the business work that caused it, including retries, caches, tools, and shared infrastructure.

Concept overview

Token cost allocation maps model usage to a tenant, team, workflow, or product feature. It requires more than multiplying a final response’s token count by a price: retries, planning calls, embedding requests, cache reads or writes, multimodal inputs, and failed attempts can all contribute. Self-hosted inference also needs infrastructure cost allocation rather than provider token billing alone.

The accounting system should distinguish estimated usage at admission from observed usage and reconciled billing. Prices and billing categories vary by provider, model, region, and contract, so a versioned rate catalog is essential. Allocation is an operational and financial measurement system; it should not expose sensitive prompt contents merely to identify ownership.

Why it matters in production

Proof of concept

A prototype tags every model call with a workflow and feature identifier and compares estimates with returned usage.

Production

Production records attempt-level usage, rate versions, cache categories, and unattributed cost exceptions.

Enterprise scale

Enterprise scale reconciles invoices, allocates shared capacity with documented rules, and connects budgets to admission without silently blocking essential workflows.

Architecture components

Usage envelope

Carries tenant, feature, workflow, and attempt identifiers through inference calls.

Provider usage adapter

Normalizes model-specific reported usage while preserving original categories.

Rate catalog

Stores effective prices and contractual dimensions by date and model.

Cost ledger

Records immutable estimated, observed, and reconciled amounts.

Budget and reporting service

Aggregates ownership and informs quotas, alerts, and capacity decisions.

The architecture, mapped

Runtime flow

  1. 1

    Assign ownership

    Attach a stable cost center and workflow identity before any model or embedding call.

  2. 2

    Estimate admission cost

    Use input size and output limits to reserve an approximate budget.

  3. 3

    Record every attempt

    Capture provider, model, usage categories, cache behavior, and retry relationships.

  4. 4

    Apply versioned rates

    Calculate observed cost using the rate effective for the actual usage event.

  5. 5

    Reconcile totals

    Compare the ledger with provider billing or infrastructure allocation and investigate differences.

  6. 6

    Report accepted-task economics

    Include failures and retries when comparing routes or product features.

Allocating assistant spend across product features

Enterprise collaboration · Illustrative enterprise scenario, not a reported customer outcome.

Business situation

A collaboration platform offers document summaries, meeting follow-ups, and workspace search to several business units.

The problem

Shared provider invoices cannot explain which features generate retries or expensive long-context work.

Agent requirement

Attribute complete accepted-task cost without logging private document text.

Architecture

Usage envelopes connect every inference attempt to feature and business-unit identifiers, and a ledger applies effective rates.

Runtime

  • A summary task records its planner, generation, and retry calls under one workflow.
  • Reports compare total cost with accepted results and reconcile unexplained provider charges.

Failure scenario

If a provider omits final usage after a broken stream, the ledger retains an estimate and marks it pending reconciliation.

Operational impact

Measure unattributed spend, reconciliation variance, and cost per accepted task; a low reported average is misleading when failed attempts are excluded.

Architecture tradeoffs

DecisionBenefitCost
Fine-grained attributionReveals costly workflow stages.Increases event volume and ownership metadata management.
Admission estimatesSupport proactive budget control.Differ from actual generation and billing.
Shared infrastructure allocationEnables self-hosted chargeback.Requires an agreed rule for idle and reserved capacity.

Failure scenarios & recovery

Retry cost is double-counted or omitted

Detect: Ledger totals diverge from attempt records.

Recover: Use unique usage-event IDs and explicit retry relationships.

Price change rewrites history

Detect: Historical reports change unexpectedly.

Recover: Apply effective-dated rates and immutable reconciled entries.

Common architecture mistakes

Counting only final successful responses

Include all attempts and supporting model work.

Hardcoding current prices

Use a versioned provider and contract rate catalog.

Equating tokens with all infrastructure cost

Account for idle, storage, network, and accelerator allocation where relevant.

When to choose this pattern

Choose it when

  • Use for multi-tenant products and shared AI platforms.
  • Use when routing and caching decisions need economic evidence.
  • Use for budget alerts and documented chargeback.

Avoid it when

  • Avoid exposing raw prompts in accounting records.
  • Do not treat estimates as final invoices.
  • Avoid cost comparisons that ignore task acceptance quality.

Architecture checklist

  • Tag every attempt before execution.
  • Preserve provider usage categories.
  • Version prices by effective date.
  • Deduplicate usage events.
  • Reconcile missing and unattributed charges.
  • Report cost per accepted task including retries.
