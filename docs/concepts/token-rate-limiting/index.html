33 — Token Rate Limiting

Enforce token-based admission and consumption budgets so individual requests and tenants cannot exhaust shared inference capacity or spend.

Concept overview

Token rate limiting controls how much input and output work a caller can consume over time. Request counts alone are insufficient because one long-context generation can cost far more than many short requests. A practical design combines request, token, concurrency, and total-budget limits according to the service's bottlenecks.

Reserve estimated capacity before dispatch and reconcile actual usage after completion. Streaming and tool loops make final consumption uncertain, so include output ceilings and a policy for interrupted or missing usage reports. Local limits must coordinate with provider quotas without assuming the provider measures the same units or time windows.

Why it matters in production

Proof of concept

A prototype can log token usage by request and derive realistic demand distributions. Avoid setting limits solely from average prompt size.

Production

Production applies per-user and per-tenant admission, bounded output, concurrency caps, and clear retry guidance. Accounting must be atomic enough to prevent concurrent requests overspending the same allowance.

Enterprise scale

At scale, distributed limiters balance consistency and latency. Allocate capacity fairly, protect critical workflows, and monitor reserved versus consumed tokens to avoid both overload and unnecessary rejection.

Architecture components

Usage estimator

Predicts input and bounded output demand for admission decisions.

Quota store

Maintains tenant, user, and global allowances with atomic reservation semantics.

Admission controller

Accepts, queues, or rejects requests according to token and concurrency capacity.

Consumption meter

Collects actual usage from completed and interrupted model calls.

Reconciler

Releases unused reservations and charges actual consumption under documented accounting rules.

Protecting a shared document assistant

Enterprise SaaS · Illustrative enterprise scenario, not a reported customer outcome.

Business situation

A SaaS provider serves tenants whose document sizes and user activity differ substantially.

The problem

A few bulk users can consume the provider quota and make ordinary interactive requests fail for every tenant.

Agent requirement

The assistant must provide predictable service while keeping tenant spending and shared capacity within limits.

Architecture

A token limiter combines tenant allowances with global concurrency and a separate pool for approved batch work.

Runtime

  • An interactive request reserves its estimated input and maximum output before reaching the model endpoint.
  • The final usage report releases unused capacity, while batch work waits in a lower-priority queue during contention.

Failure scenario

If a worker crashes before reconciliation, a reservation lease expires into a documented conservative accounting path rather than remaining locked forever.

Operational impact

Track admitted tokens, rejected demand, reservation waste, queue delay, and fairness across tenants. Request count alone would conceal the largest consumers.

Failure scenarios & recovery

Concurrent requests overspend one allowance

Detect: Ledger totals exceed the configured limit under load tests.

Recover: Use atomic reservation or bounded partitioned quotas.

A missing usage report leaves capacity reserved

Detect: Reservation age exceeds its lease.

Recover: Reconcile from provider evidence or apply the documented fallback charge.

Common architecture mistakes

Limiting only requests per minute

Include tokens and concurrency for variable-sized work.

Charging only successful responses

Account for consumed work on failures and cancellations.

Returning retry guidance without a real window

Derive retry behavior from actual limiter state.

When to choose this pattern

Choose it when

  • Inference capacity or spend is shared across callers.
  • Prompt and output sizes vary materially.
  • Provider quotas need application-level protection.

Avoid it when

  • Workload size is fixed and simple request limits suffice.
  • Usage cannot be measured or bounded meaningfully.
  • A limiter is being used to hide inadequate capacity planning.

Architecture checklist

  • Define budget owners and applicable windows.
  • Reserve capacity atomically before dispatch.
  • Set output and concurrency ceilings.
  • Reconcile failures and cancellations.
  • Expire abandoned reservations safely.
  • Measure tenant fairness and reservation waste.
