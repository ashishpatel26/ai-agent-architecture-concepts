Resilience, Reliability & Failure Handling

46 — Max Iterations Fallback

Terminate agent loops predictably when iteration, time, cost, or progress limits are reached, returning an honest partial outcome and a controlled next step.

OverviewWhy it mattersComponentsArchitecture diagramsRuntime flowIndustry use caseTradeoffsFailure scenariosCommon mistakesWhen to use / avoidArchitecture checklistRelated conceptsPrimary references

Concept overview

A maximum-iterations fallback prevents an agent from continuing indefinitely when it repeats actions, cannot resolve uncertainty, or never emits a valid completion signal. Count the events that consume meaningful work: model turns, tool attempts, sub-agent calls, and repair loops may need separate counters. One global counter should still bound the complete parent task.

An iteration ceiling is a final containment mechanism, not a quality strategy. Combine it with elapsed-time, token, cost, and progress checks. When the limit is reached, stop starting new work, reconcile in-flight effects, and produce a defined terminal state rather than inventing a successful answer from incomplete evidence.

Why it matters in production

Proof of concept

A prototype should have a small explicit ceiling and log why runs stop. Examine trajectories that hit the limit before increasing it.

Production

Production reserves budget for finalization, cancellation, and safe result delivery. Nested agents and correction loops must consume inherited parent budgets rather than resetting their own unlimited counters.

Enterprise scale

At scale, tune limits by task class using observed success curves and marginal quality gains. Repeated limit exhaustion may reveal a broken tool, ambiguous objective, or routing error rather than unusually difficult work.

Architecture components

Budget counter

Tracks iterations, tool attempts, tokens, cost, and elapsed time across the full task tree.

Progress detector

Identifies repeated actions, unchanged evidence, and unresolved requirements without improvement.

Loop admission gate

Decides whether another step may start while reserving finalization capacity.

Termination handler

Cancels optional work and reconciles any in-flight side effects.

Fallback response

Reports completed work, missing evidence, stop reason, and an appropriate next action.

The architecture, mapped

Runtime flow

  1. 1

    Initialize limits

    Assign task-class ceilings and reserve resources for finalization and recovery.

  2. 2

    Charge every step

    Increment counters consistently across model calls, tools, retries, and delegated work.

  3. 3

    Check progress

    Compare new evidence and unresolved requirements to detect ineffective repetition.

  4. 4

    Deny further work

    Stop admission when any hard limit or no-progress condition is met.

  5. 5

    Reconcile activity

    Cancel safe optional tasks and determine outcomes of already-started commands.

  6. 6

    Return terminal result

    Publish a partial, failed, or review-required state with verified artifacts and a clear reason.

Bounding a configuration investigation

Enterprise IT · Illustrative enterprise scenario, not a reported customer outcome.

Business situation

An IT assistant investigates why a business application cannot connect to an approved database endpoint.

The problem

A missing permission causes repeated discovery calls, and the model keeps rephrasing the same query without obtaining new evidence.

Agent requirement

The assistant must stop predictably and hand an administrator the useful diagnostics already collected.

Architecture

A loop governor tracks tool fingerprints, evidence changes, and the shared iteration and time budget.

Runtime

  • The agent verifies network reachability and retrieves a permission error, then repeats an equivalent lookup.
  • The no-progress detector stops further investigation and prepares a package containing confirmed checks and the unresolved access requirement.

Failure scenario

If a diagnostic task is still running, it is cancelled where supported; any completed administrative action is reconciled before final status is reported.

Operational impact

Measure limit-hit rate, repeated calls, useful partial results, and completion probability by allowed iteration count. Raising ceilings should require evidence of additional value.

DecisionBenefitCost
Hard ceilingsCost and runtime exposure become bounded.Some difficult legitimate tasks stop before completion.

Reserved finalization budgetThe system can explain and reconcile a stopped run.Less budget remains for primary investigation.

Failure scenarios & recovery

A child loop resets its counter repeatedly

Detect: Parent accounting shows missing delegated consumption.

Recover: Charge child steps to inherited budgets and reject untracked work.

The limit fires after a command begins

Detect: Tool outcome remains pending when the loop stops.

Recover: Reconcile the command instead of declaring all work cancelled.

Common architecture mistakes

Returning a confident answer after forced termination

Mark missing evidence and partial completion explicitly.

Counting only model turns

Include tools, retries, and delegated work.

Increasing limits without trajectory review

Diagnose repeated failure patterns first.

When to choose this pattern

Choose it when

  • Agents can iterate or delegate dynamically.
  • Cost and completion time need hard upper bounds.
  • Partial results or escalation are meaningful outcomes.

Avoid it when

  • A fixed acyclic workflow already has a known bounded path.
  • The fallback would misrepresent incomplete work as success.
  • The design cannot reconcile in-flight side effects.

Architecture checklist

  • Define counters for every work type.
  • Share budgets across child tasks.
  • Reserve finalization capacity.
  • Detect repeated actions and stagnant evidence.
  • Reconcile commands before terminal status.
  • Review limit-hit trajectories by task class.
