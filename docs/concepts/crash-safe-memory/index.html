Resilience, Reliability & Failure Handling

57 — Crash-Safe Memory

Persist agent progress and effect receipts so a replacement worker can resume safely after an abrupt process or machine failure.

OverviewWhy it mattersComponentsArchitecture diagramsRuntime flowIndustry use caseTradeoffsFailure scenariosCommon mistakesWhen to use / avoidArchitecture checklistRelated conceptsPrimary references

Concept overview

Crash-safe memory preserves the workflow facts needed for correct recovery after volatile process state disappears. It includes accepted inputs, state revisions, pending commands, tool receipts, and completion markers. Saving conversation text alone cannot establish whether an external operation happened before a crash.

The critical design question is the commit boundary. Durable state must precede acknowledgment, and external effects need idempotency or reconciliation when they cannot share a transaction with workflow storage. Write-ahead logging protects a database transaction under its configured durability assumptions; it does not automatically make the surrounding distributed workflow exactly once.

Why it matters in production

Proof of concept

A prototype should survive a forced process kill between two tool calls without losing the accepted task.

Production

Production persists revisions and effect identifiers, coordinates queue acknowledgment with durable commits, and tests duplicate delivery.

Enterprise scale

Enterprise scale defines recovery point and recovery time objectives, replication behavior, backup restoration, and schema compatibility for old unfinished workflows.

Architecture components

Durable state database

Stores workflow revisions and committed task progress.

Command outbox

Records intended external work in the same transaction as its originating state change.

Receipt ledger

Associates tool results with stable operation identifiers.

Recovery worker

Acquires a lease and reconstructs pending work after failure.

Snapshot archive

Provides recoverable history beyond a single running database instance.

The architecture, mapped

Runtime flow

  1. 1

    Accept durably

    Commit the task identifier and initial state before acknowledging receipt to the caller.

  2. 2

    Record intent

    Write the next state and tool command together using a transaction or equivalent atomic boundary.

  3. 3

    Execute command

    Deliver the command with a stable idempotency key and retain its external receipt.

  4. 4

    Commit outcome

    Persist validated results and mark the command complete before advancing the workflow.

  5. 5

    Recover ownership

    A replacement worker acquires a fenced lease and reads the last committed revision.

  6. 6

    Resolve uncertainty

    Reconcile incomplete commands against external receipts before deciding whether execution may repeat.

Surviving a crash during account-maintenance review

Banking operations · Illustrative enterprise scenario, not a reported customer outcome.

Business situation

An internal agent verifies supporting documents and submits approved account-maintenance requests.

The problem

A worker can crash after submission but before recording the response.

Agent requirement

Recover the review without submitting the maintenance request twice.

Architecture

The workflow database stores command intent, a stable case key, and the maintenance-system receipt.

Runtime

  • The replacement worker finds a pending submission for the case.
  • It queries the maintenance system by the original key and records the existing receipt.

Failure scenario

If the external system cannot identify the submission, the case pauses for reconciliation instead of assuming failure.

Operational impact

Measure recovered task completeness, duplicate-effect incidents, and reconciliation age; memory durability is useful only when business effects remain coherent.

Architecture tradeoffs

DecisionBenefitCost
Synchronous durable commitReduces acknowledged-progress loss.Adds write latency to each boundary.
Checkpoint batchingImproves write throughput.Increases replay distance and possible unacknowledged work.
Replicated storageImproves resilience to node loss.Requires explicit consistency and failover assumptions.

Failure scenarios & recovery

Acknowledgment precedes persistence

Detect: An accepted task disappears after restart.

Recover: Persist acceptance before acknowledging and replay durable ingress records.

Lease split brain

Detect: Two workers attempt the same revision.

Recover: Reject stale fencing tokens and reconcile any external effects.

Common architecture mistakes

Persisting only model messages

Store workflow state, tool intent, and effect receipts.

Assuming database durability covers APIs

Design idempotency and reconciliation across the external boundary.

Never testing abrupt termination

Inject kills at every commit boundary and inspect recovered invariants.

When to choose this pattern

Choose it when

  • Use for long-running or high-value workflows.
  • Use with at-least-once queues and replaceable workers.
  • Use when accepted work must survive machine loss.

Avoid it when

  • Avoid durable orchestration for disposable stateless inference.
  • Do not promise zero data loss without storage guarantees.
  • Avoid automatic replay of ambiguous non-idempotent commands.

Architecture checklist

  • Define the durable acknowledgment boundary.
  • Persist command identity before execution.
  • Fence recovered workers.
  • Test crashes between effect and receipt commit.
  • Document replication and backup recovery objectives.
  • Exercise restoration of unfinished workflow schemas.
