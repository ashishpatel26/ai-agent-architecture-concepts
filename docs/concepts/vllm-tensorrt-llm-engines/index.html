88 — vLLM / TensorRT-LLM Engines

Treat the inference engine as a scheduled memory-and-compute system whose configuration must match models, hardware, and service objectives.

Concept overview

Inference engines such as vLLM and TensorRT-LLM implement the runtime beneath model APIs. They manage request scheduling, attention-cache allocation, batching, optimized kernels, and often distributed execution. Their main contribution is efficient execution of supported model workloads, not automatic improvement in model reasoning or application correctness.

Engine capabilities and compatibility vary by release, model architecture, precision, and hardware. A configuration optimized for long offline batches may damage interactive time to first token. Evaluate prefill and decoding separately, account for key-value cache growth, and compare complete service behavior rather than one maximum-throughput benchmark.

Why it matters in production

Proof of concept

A prototype serves the actual model and measures realistic prompt and completion distributions on target hardware.

Production

Production pins engine and driver versions, validates model features, and sets queue, sequence, and memory limits.

Enterprise scale

Enterprise scale manages heterogeneous fleets, distributed placement, engine upgrades, and capacity models grounded in service-level latency and quality constraints.

Architecture components

API frontend

Validates requests and translates application settings into supported engine parameters.

Request scheduler

Admits and batches prefill and decoding work.

KV cache manager

Allocates sequence state and reclaims it on completion or cancellation.

Execution backend

Runs compatible kernels across the selected accelerator topology.

Engine telemetry

Reports queueing, token throughput, cache pressure, and errors.

The architecture, mapped

Runtime flow

  1. 1

    Validate compatibility

    Check model architecture, tokenizer, precision, and requested features against the pinned engine release.

  2. 2

    Profile workload shape

    Measure input lengths, output lengths, concurrency, and latency targets.

  3. 3

    Set memory and admission limits

    Budget weights, cache, activations, and overhead with measured headroom.

  4. 4

    Schedule generation

    Allow the engine to batch compatible work while respecting application deadlines.

  5. 5

    Observe and tune

    Separate queueing, prefill, decoding, and cancellation behavior before changing parameters.

  6. 6

    Upgrade by canary

    Compare outputs and service metrics on a controlled cohort before replacing the fleet.

Serving a document-answering model

Enterprise search · Illustrative enterprise scenario, not a reported customer outcome.

Business situation

A knowledge assistant serves short questions over contexts of widely varying length.

The problem

A default engine configuration admits too many long prompts and degrades interactive response time.

Agent requirement

Tune serving capacity around the real mix of prefill and decode work.

Architecture

The team pins an engine release, measures context distributions, and sets token-based admission and cache limits.

Runtime

  • Long-context requests enter a bounded queue instead of exhausting cache.
  • Telemetry separates prefill delay from decoding speed so tuning targets the actual bottleneck.

Failure scenario

If an engine upgrade changes structured-output behavior or memory use, the canary is rolled back before fleet expansion.

Operational impact

Measure accepted throughput at the latency objective, not unconstrained tokens per second; a faster benchmark can still produce a worse interactive service.

Failure scenarios & recovery

KV cache exhaustion

Detect: Allocation failures correlate with active sequence tokens.

Recover: Reduce admission and adjust context or concurrency limits.

Engine feature mismatch

Detect: Tool schemas or sampling settings behave unexpectedly.

Recover: Validate the supported contract and use an evaluated configuration.

Common architecture mistakes

Copying benchmark settings unchanged

Tune with the service’s real request distribution.

Ignoring driver and tokenizer versions

Version the complete execution bundle.

Maximizing throughput without latency constraints

Optimize accepted throughput under the actual service objective.

When to choose this pattern

Choose it when

  • Use for self-hosted models at meaningful concurrency.
  • Use when engine-level scheduling or memory efficiency matters.
  • Use when hardware-specific optimization justifies operational ownership.

Avoid it when

  • Avoid self-hosting solely because an engine exists.
  • Do not assume feature parity across releases and backends.
  • Avoid unsupported quantization or model combinations.

Architecture checklist

  • Pin model, engine, driver, and tokenizer.
  • Benchmark realistic length distributions.
  • Budget KV cache explicitly.
  • Measure prefill and decode separately.
  • Test cancellation and overload behavior.
  • Canary every engine upgrade.
