89 — Serverless LLM Architecture

Separate request admission from elastic inference capacity so serverless execution can scale safely despite model startup and duration constraints.

OverviewWhy it mattersComponentsArchitecture diagramsRuntime flowIndustry use caseTradeoffsFailure scenariosCommon mistakesWhen to use / avoidArchitecture checklistRelated conceptsPrimary references

Concept overview

Serverless LLM architecture delegates capacity provisioning to a platform while the application supplies request handling, model execution, or orchestration. It may use managed inference, GPU containers, functions that call hosted models, or asynchronous workers. Serverless does not imply that a large model fits a short-lived general-purpose function or starts instantly.

The core architecture decouples interactive deadlines from elastic startup. A gateway can serve warm capacity for interactive work and place delay-tolerant tasks in a durable queue. State, idempotency, and artifacts remain external to ephemeral workers. Platform-specific concurrency, duration, accelerator, and scaling limits must be verified before committing to the design.

Why it matters in production

Proof of concept

A prototype measures both warm and cold behavior and confirms the platform can run the intended model or API orchestration.

Production

Production uses durable queues, external state, bounded concurrency, and clear synchronous versus asynchronous contracts.

Enterprise scale

Enterprise scale manages regional quotas, startup storms, cost visibility, and minimum capacity for workloads that cannot tolerate scale-from-zero delay.

Architecture components

Request gateway

Authenticates requests and selects synchronous or asynchronous handling.

Durable queue

Buffers accepted delayed work with stable task identifiers.

Elastic inference workers

Load approved artifacts and execute within platform resource limits.

External state store

Persists task status, results, and idempotency records.

Autoscaling controller

Adjusts capacity using backlog, concurrency, and startup lead time.

The architecture, mapped

Runtime flow

  1. 1

    Classify latency needs

    Decide whether the task requires immediate response or can return a job identifier.

  2. 2

    Accept work durably

    Persist task identity and enqueue before acknowledging asynchronous acceptance.

  3. 3

    Scale compatible capacity

    Request workers with the required accelerator, memory, and runtime support.

  4. 4

    Initialize and execute

    Wait for real readiness, then run the task under deadline and resource limits.

  5. 5

    Persist the result

    Commit validated output and completion before acknowledging queue delivery.

  6. 6

    Scale down safely

    Drain active work and rely on external state for later retries or status queries.

Processing periodic inspection reports

Property services · Illustrative enterprise scenario, not a reported customer outcome.

Business situation

A property platform summarizes inspection documents uploaded in bursts after site visits.

The problem

Keeping peak GPU capacity running continuously is expensive, but reports can tolerate queued processing.

Agent requirement

Scale processing with demand while preserving every accepted report and its status.

Architecture

Uploads create durable jobs consumed by elastic inference workers; results remain in external storage.

Runtime

  • The user receives a job identifier after durable acceptance.
  • A worker starts, loads the approved model, processes the report, and commits the result.

Failure scenario

If the worker exceeds its execution limit, the queue retries the same task identity and avoids duplicate accepted results.

Operational impact

Measure job completion age, cold-start contribution, cost per accepted report, and retry volume; low idle cost must be weighed against delayed availability.

Architecture tradeoffs

DecisionBenefitCost
Scale to zeroReduces idle compute spending.Adds cold-start delay and capacity uncertainty.
Durable asynchronous processingAbsorbs bursts and worker loss.Requires job status and delayed-result interfaces.
Minimum warm capacityProtects interactive latency.Reduces the economic benefit of zero idle workers.

Failure scenarios & recovery

Burst exceeds platform quota

Detect: Backlog rises while worker count stops increasing.

Recover: Apply admission limits and expose realistic deferred status.

Worker terminates before result commit

Detect: The queue redelivers an apparently unfinished task.

Recover: Use stable IDs and transactional completion records.

Common architecture mistakes

Assuming serverless means stateless business logic

Persist task progress and results externally.

Ignoring cold-start distributions

Measure the full time to useful capacity.

Using unlimited queue acceptance

Bound backlog according to retention and completion objectives.

When to choose this pattern

Choose it when

  • Use for bursty delay-tolerant inference jobs.
  • Use when platform-managed capacity fits the model requirements.
  • Use for lightweight orchestration around hosted inference.

Avoid it when

  • Avoid scale-to-zero for strict low-latency workloads without warm capacity.
  • Do not assume accelerator availability in every platform tier.
  • Avoid long tasks that exceed supported execution limits.

Architecture checklist

  • Verify platform resource and duration limits.
  • Measure cold and warm latency.
  • Persist accepted jobs before acknowledgment.
  • Bound backlog and concurrency.
  • Make retries idempotent.
  • Track cost and completion age together.
