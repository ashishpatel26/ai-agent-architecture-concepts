67 — Graph RAG / Knowledge Graphs

Combine entity relationships with source passages to answer connection-oriented questions that isolated similarity matches cannot resolve.

Concept overview

Graph RAG uses an explicit relationship representation to guide retrieval or synthesis. A knowledge graph can represent suppliers, facilities, products, incidents, and their connections; linked source passages provide the evidence behind each node or edge. Some GraphRAG approaches additionally build community summaries for corpus-wide questions. These are design choices, not a single interchangeable algorithm.

The graph is a derived evidence structure, not unquestionable truth. Entity resolution, relation extraction, temporal validity, and provenance determine its usefulness. A graph traversal can expose a possible path, but the answer must distinguish asserted relationships from inferred connections and must respect permissions on every contributing source.

Why it matters in production

Proof of concept

A prototype models one narrow relationship question and manually checks extracted entities and edges.

Production

Production attaches provenance, confidence, validity intervals, and access metadata while evaluating both extraction and retrieval.

Enterprise scale

Enterprise scale requires incremental graph updates, entity merge governance, traversal limits, and recomputation rules for summaries affected by source changes.

Architecture components

Entity resolver

Maps mentions to stable identities while preserving ambiguous matches.

Relation extractor

Produces typed edges with source evidence and temporal attributes.

Graph store

Supports bounded traversal and relationship filtering.

Passage index

Retrieves original text supporting graph nodes and edges.

Graph-guided retriever

Combines traversal results, source passages, and optional community summaries.

  3. 3

  6. 6

    Cite relationships and identify uncertainty instead of presenting inferred edges as established facts.

Tracing a shared upstream dependency

Supply chain · Illustrative enterprise scenario, not a reported customer outcome.

Business situation

A manufacturer investigates whether several delayed parts depend on the same upstream processing facility.

The problem

Part-level document search finds separate supplier notes but does not connect their facility references.

Agent requirement

Expose the dependency path with dated evidence and uncertainty.

Architecture

A graph connects suppliers, facilities, and parts; each edge links to an approved source passage.

Runtime

  • The question resolves affected part IDs and traverses supplier-to-facility edges.
  • The agent fetches supporting notes and reports a shared facility only where the evidence supports it.

Failure scenario

An ambiguous facility name remains two possible entities until reviewed, preventing a false shared-dependency conclusion.

Operational impact

Measure supported-path precision, entity-resolution errors, and evidence freshness; graph density alone is not a quality metric.

Architecture tradeoffs

DecisionBenefitCost
Explicit relationshipsSupport multi-hop dependency questions.Require extraction and identity maintenance.
Community summariesHelp answer corpus-wide themes.Can obscure source-level detail and become stale.
Strict provenanceMakes relationships auditable.Increases storage and retrieval work.

Failure scenarios & recovery

Incorrect entity merge

Detect: Unrelated organizations share an apparent dependency.

Recover: Split the entity and recompute affected edges and summaries.

Expired relation remains active

Detect: A traversal uses an obsolete supplier relationship.

Recover: Filter by validity interval and reconcile source updates.

Common architecture mistakes

Treating extracted edges as facts

Retain source evidence and uncertainty.

Allowing unbounded traversal

Limit depth, relation types, and result cardinality.

Ignoring permissions on summaries

Authorize every contributing source or build scope-specific summaries.

When to choose this pattern

Choose it when

  • Use for dependency, ownership, and relationship questions.
  • Use when repeated entity connections matter across documents.
  • Use for corpus-level synthesis with maintained provenance.

Avoid it when

  • Avoid graphs for simple isolated fact lookup.
  • Avoid automatic entity merging without quality controls.
  • Do not deploy when source relationships cannot be kept current.

Architecture checklist

  • Define a narrow graph schema.
  • Preserve edge-level provenance.
  • Represent ambiguous identities.
  • Version temporal relationships.
  • Enforce traversal and access limits.
  • Evaluate supported paths against expert labels.
