69 — Vector Database Scaling (Pinecone/Milvus)

Scale vector retrieval by separating storage, indexing, query capacity, tenancy, and ingestion while measuring recall under real constraints.

Concept overview

Vector database scaling is a capacity and correctness problem across several dimensions: vector count, dimensionality, metadata size, query rate, update rate, and filter selectivity. Approximate nearest-neighbor indexes trade search work and memory for recall. Adding replicas may increase read capacity, while sharding changes data distribution and query fan-out.

Managed and self-operated systems expose different operational boundaries, so capacity planning must use the selected product’s behavior rather than assume interchangeable guarantees. Consistency, index readiness, deletion visibility, and metadata filtering affect application correctness. A successful upsert acknowledgment does not necessarily mean every subsequent search immediately sees the change.

Why it matters in production

Proof of concept

A prototype uses representative vectors and metadata rather than a tiny unfiltered sample.

Production

Production benchmarks recall and tail latency under concurrent reads, writes, and selective filters, then sets capacity and freshness objectives.

Enterprise scale

Enterprise scale introduces tenant placement, hot-partition handling, rebuild planning, disaster recovery, and cost models covering replicas, storage, and re-embedding.

Architecture components

Ingestion workers

Validate vectors and metadata and write versioned records idempotently.

Index partitions

Distribute vector and scalar data across storage and compute boundaries.

Query replicas

Provide search capacity with explicit health and index readiness.

Routing layer

Selects tenant partitions and merges results across required shards.

Capacity telemetry

Tracks latency, recall samples, memory, ingestion lag, and hot partitions.

The architecture, mapped

Runtime flow

  1. 1

    Profile the workload

    Measure vector sizes, metadata cardinality, query shapes, and update frequency.

  2. 2

    Choose partitioning

    Align tenant isolation and expected access patterns while avoiding oversized hotspots.

  3. 3

    Build and validate indexes

    Check dimensions, metric choice, and recall against an exact-search sample.

  4. 4

    Serve constrained queries

    Route to relevant partitions and apply supported filters with bounded fan-out.

  5. 5

    Scale the bottleneck

    Add read replicas, rebalance partitions, or tune indexes according to observed pressure.

  6. 6

    Rebuild safely

    Create a new index version, validate it, and switch routing with a rollback path.

Scaling a multilingual product knowledge index

E-commerce · Illustrative enterprise scenario, not a reported customer outcome.

Business situation

A marketplace assistant searches product specifications across many sellers and frequent catalog updates.

The problem

A few large sellers create hot partitions while promotions increase query volume and update traffic.

Agent requirement

Maintain scoped retrieval quality without letting one seller consume the whole search tier.

Architecture

Tenant-aware routing combines partition limits, read replicas, and versioned ingestion checkpoints.

Runtime

  • A query targets only authorized seller partitions.
  • The platform monitors selective-filter latency and splits an oversized partition after validating the new placement.

Failure scenario

If a new index revision lags or loses recall, routing returns to the previous validated revision.

Operational impact

Measure recall, p95 search latency, index visibility lag, and cost per workload class; raw vector count does not determine required capacity alone.

Architecture tradeoffs

DecisionBenefitCost
More replicasIncrease read capacity and availability.Multiply memory and synchronization cost.
More shardsDistribute large datasets.Increase fan-out, merging, and operational complexity.
Aggressive approximationReduces search work.May lose relevant evidence, especially under selective filters.

Failure scenarios & recovery

Hot tenant overwhelms one partition

Detect: Tenant-specific latency diverges from fleet averages.

Recover: Apply quotas and repartition with controlled migration.

Embedding dimension changes midstream

Detect: Writes fail or incompatible vectors coexist.

Recover: Use a separate versioned index and explicit routing migration.

Common architecture mistakes

Benchmarking only unfiltered queries

Include real ACL and metadata predicates.

Scaling replicas to fix ingestion bottlenecks

Identify the constrained subsystem first.

Migrating embeddings in place

Build and validate a parallel index before switching.

When to choose this pattern

Choose it when

  • Use for growing corpora or sustained concurrent retrieval.
  • Use when tenant skew affects latency.
  • Use when updates and queries need separate capacity planning.

Avoid it when

  • Avoid distributed indexing for a small stable corpus without need.
  • Do not assume immediate read visibility after writes.
  • Do not trade away recall without downstream evaluation.

Architecture checklist

  • Benchmark representative filtered workloads.
  • Measure recall against an exact baseline.
  • Document consistency and visibility behavior.
  • Plan hot-tenant limits.
  • Version embedding and index schemas.
  • Exercise rebuild and restore procedures.
