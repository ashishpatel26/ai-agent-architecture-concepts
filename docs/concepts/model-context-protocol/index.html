101 — Model Context Protocol (MCP)

Standardize how agent hosts discover and invoke external capabilities while keeping trust, authorization, and business policy explicit.

OverviewWhy it mattersComponentsArchitecture diagramsRuntime flowIndustry use caseTradeoffsFailure scenariosCommon mistakesWhen to use / avoidArchitecture checklistRelated conceptsPrimary references

Concept overview

MCP defines a protocol boundary between an application hosting an agent, its protocol clients, and servers exposing capabilities such as tools, resources, and prompts. It reduces custom integration plumbing; it does not make a server trustworthy or decide whether a proposed business action is authorized.

Treat discovery metadata and tool results as external input. The host still owns user intent, capability selection, approval policy, and result handling. Pin the supported protocol version and test the capabilities actually negotiated: a common envelope cannot guarantee identical semantics across independently implemented servers.

Why it matters in production

Proof of concept

A proof of concept may connect one trusted local server and inspect tool results manually; record which capabilities and transport assumptions it relies on.

Production

Production requires server registration, schema validation, scoped credentials, operation timeouts, and explicit approval rules for mutating tools before enabling discovery broadly.

Enterprise scale

Enterprise scale adds server ownership, version compatibility testing, per-tenant connection policy, capacity limits, and auditable capability changes across many teams.

Architecture components

Agent host

Owns user interaction, model context, tool policy, and approval boundaries.

Protocol client

Negotiates capabilities and manages the transport lifecycle for a server connection.

Registered MCP server

Exposes approved capabilities and validates incoming requests before calling downstream systems.

Authorization gateway

Enforces identity, audience, scope, resource access, and operation policy independently of model output.

Evidence and telemetry store

Records tool version, sanitized inputs, result status, and downstream operation identifiers.

The architecture, mapped

Runtime flow

  1. 1

    Select trusted connection

    Resolve the server from an administratively controlled registry with an owner and supported protocol version.

  2. 2

    Negotiate capabilities

    Initialize the connection and record available capabilities; reject unsupported requirements rather than assuming every server behaves identically.

  3. 3

    Bind authority

    Establish transport-appropriate credentials and downstream resource policy; never equate successful connection with permission for every tool.

  4. 4

    Validate invocation

    Check the chosen tool, argument schema, resource scope, deadline, and any required action approval before sending the request.

  5. 5

    Handle external output

    Validate result shape, preserve provenance, and treat returned text as evidence rather than new governing instructions.

  6. 6

    Reconcile effects

    For mutations, retain a stable operation identifier and query uncertain downstream outcomes before considering a retry.

Scoped support knowledge connector

Enterprise software · Illustrative enterprise scenario, not a reported customer outcome.

Business situation

Illustrative architecture: A support assistant needs governed access to product documentation and customer case summaries through separately owned integrations.

The problem

Custom adapters duplicate connection logic, but broad connector credentials would expose unrelated customer cases.

Agent requirement

Provide interoperable discovery while enforcing customer assignment and read-only access for this workflow.

Architecture

The host connects only to registered servers; a case service rechecks the authenticated support user's tenant and case scope.

Runtime

  • Resolve approved server
  • negotiate supported capabilities
  • retrieve allowed tool schemas
  • validate case scope
  • call the read tool
  • return cited evidence

Failure scenario

A server advertises a new write tool; host policy withholds it until the owner reviews its schema and action semantics.

Operational impact

Measure integration maintenance effort, denied unauthorized requests, tool error rate, and evidence correctness; interoperability alone does not establish safety or quality.

Architecture tradeoffs

DecisionBenefitCost
Standard protocol boundaryReduces repeated connector plumbing.Still requires server-specific semantic and security review.
Dynamic capability discoveryAllows integrations to evolve without hardcoding every tool.Unexpected metadata changes need policy gates and compatibility checks.
Remote server transportCentralizes connector operations and updates.Introduces network latency, identity management, and availability dependencies.

Failure scenarios & recovery

A tool result contains instructions to disclose credentials.

Detect: Result handling detects an attempted action outside the authorized task and tool scope.

Recover: Treat the text as untrusted evidence, block the action, and record the offending server response.

A connection drops after a mutating downstream call.

Detect: The host has a submitted operation identifier but no confirmed result.

Recover: Query the business system through a safe status path before retrying with the same logical operation key.

Common architecture mistakes

Assuming protocol compliance implies trusted tools.

Review server ownership, downstream access, and mutation semantics separately.

Passing one unrestricted credential through every server.

Use scoped, audience-bound credentials and enforce resource authorization at the service boundary.

Letting tool descriptions override host instructions.

Keep discovery content in an untrusted data channel and apply host-owned capability policy.

When to choose this pattern

Choose it when

  • Multiple agent hosts need a shared integration contract with independently maintained tools.
  • Connector teams can own versioning, authorization, and operational support for their servers.
  • A controlled capability registry can govern which tools each workflow may discover and invoke.

Avoid it when

  • One fixed API call needs no discovery or shared connector ecosystem.
  • The proposed server cannot enforce resource access or provide a reliable ownership model.
  • Hard real-time control would depend on remote model-driven tool selection.

Architecture checklist

  • Pin and test the supported protocol version and negotiated capabilities.
  • Register each server owner, transport, trust boundary, and incident contact.
  • Validate tool schemas and mutation semantics before exposing them to models.
  • Enforce user, tenant, audience, and resource scope at every protected boundary.
  • Define timeouts and reconciliation for ambiguous mutating calls.
  • Treat tool metadata and results as untrusted external content.
  • Test server changes against denied-action and compatibility scenarios.
