Network incident evidence coordination

Correlate alarms, service dependencies, and change history before an operator approves network remediation.

Explore in the architecture studio

The business situation

Illustrative reference architecture. Validate requirements for your organization.

Illustrative architecture: A telecom operations center receives thousands of alarms after a regional service degradation. Teams must identify shared dependencies, determine affected services, and inspect recent changes. The illustrative system assembles incident evidence and proposes runbook steps while network operators retain production control.

Problem

Alarm volume can hide the initiating fault, topology may be stale, and a recent change can be coincidental. A model-driven rollback without current dependency checks could widen an outage or interrupt unaffected customers.

Why a multi-agent system?

Alarm triage, topology analysis, change investigation, and runbook specialists work in parallel. Deterministic correlation rules and topology queries produce the affected-service set; the orchestrator limits hypothesis loops and preserves operator ownership.

Intended outcome

The intended result is a reviewable operational decision with source evidence and explicit ownership. Track preparation time and diagnostic quality alongside service restoration outcomes. The architecture should make uncertainty and action boundaries visible during pressure, rather than reward fluent incident narratives that outpace the evidence.

Architecture diagrams

Runtime flow

  1. 1

    Open incident context

    Deduplicate alarm bursts, assign an incident commander, and establish observation windows and diagnostic budgets.

  2. 2

    Correlate symptoms

    Group alarms using configured rules and retain representative raw events so compression cannot hide distinct failures.

  3. 3

    Trace impact

    Query service dependencies with inventory freshness metadata and separate confirmed affected services from possible exposure.

  4. 4

    Inspect changes

    Compare incident timing with approved changes and configuration differences; label causal hypotheses as provisional.

  5. 5

    Stage diagnostic plan

    Present safe diagnostic steps, expected observations, rollback prerequisites, and uncertainty for operator selection.

  6. 6

    Execute bounded action

    The gateway rechecks device state and approval scope, performs the authorized step, and evaluates service evidence before further action.

Failure recovery

Topology shows a protection path that has already failed.

Detect: Current device health disagrees with the stored dependency graph.

Recover: Mark redundancy unknown and block plans that rely on the unavailable protection path.

Repeated remediation creates an oscillating configuration.

Detect: Action history detects alternating states or an exceeded iteration budget.

Recover: Stop automation, preserve traces, and return control to the incident commander.

Security & decision boundaries

  • Never expose unrestricted device shells or configuration credentials to model prompts.
  • Bound diagnostics by device set, command allowlist, timeout, and incident budget.
  • Require operator approval for service-affecting changes and rollback execution.
  • Check topology freshness and live protection state before recommending disruption.
  • Preserve raw alarms and action receipts behind every compressed incident narrative.

Operational metrics

Measurement definitions, not promised improvements.

Incident briefing latency

Time from incident declaration to a source-backed impact and hypothesis packet.

Impact precision

Services confirmed affected divided by services flagged as affected in audited incidents.

Diagnostic usefulness

Approved diagnostics producing a discriminating observation divided by diagnostics executed.

Automation containment

Attempts blocked for exceeded device, command, or iteration scope divided by attempted actions.
