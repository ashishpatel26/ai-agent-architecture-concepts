Order recovery and returns coordination

Coordinate order status, shipment evidence, and return eligibility before committing a customer-approved resolution.

Explore in the architecture studio

The business situation

Illustrative reference architecture. Validate requirements for your organization.

Illustrative architecture: An online merchant receives a support request for an order split across two warehouses. One parcel is late, another item is damaged, and a promotion complicates refund allocation. The proposed system prepares specific resolution options without inventing shipment status or refund eligibility.

Problem

A simple refund chatbot can cancel the wrong order line, duplicate a refund after a timeout, or promise replacement inventory that is already reserved. Customer messages and uploaded images also contain untrusted instructions that must not control tools.

Why a multi-agent system?

Separate order reconciliation, shipping investigation, policy retrieval, and resolution drafting. A deterministic monetary calculator and transactional adapters own amounts and inventory reservations; agents explain the options and surface unresolved evidence.

Intended outcome

The intended result is a reviewable operational decision with source evidence and explicit ownership. Compare handling effort and customer recontacts while auditing financial effects. Faster response generation is useful only when customers receive accurate per-item status and the underlying order remains financially consistent.

Architecture diagrams

Runtime flow

  1. 1

    Authenticate request

    Bind the customer to the order and requested lines before retrieving payment or address information.

  2. 2

    Read order snapshot

    Fetch order revision, remaining refundable balance, and existing return or refund operations to avoid duplicate work.

  3. 3

    Investigate each parcel

    Parallelize shipment checks while preserving the distinction between estimated, scanned, delivered, and unknown states.

  4. 4

    Calculate valid options

    Use current inventory and deterministic amount allocation; attach the policy clause and expiry of each option.

  5. 5

    Confirm resolution

    Show the customer and support reviewer exact items, amounts, fees, and next steps; preserve unresolved damage disputes for staff.

  6. 6

    Execute and reconcile

    Submit approved actions with stable operation keys, query uncertain payment results, and report each order line's final or pending state.

Failure recovery

A refund succeeds but its response times out.

Detect: Payment lookup finds the original operation key with a completed refund.

Recover: Return the existing receipt and never create a replacement key for the same approved action.

Replacement stock disappears during confirmation.

Detect: Reservation service rejects the previously quoted stock version.

Recover: Refresh options and request new confirmation rather than silently substituting another product.

Security & decision boundaries

  • Validate customer ownership independently of order numbers pasted into chat.
  • Keep refund arithmetic and eligibility checks outside model-generated prose.
  • Bind approval to order lines, currency, amounts, and shipping destination.
  • Treat customer uploads as evidence with no authority to change system instructions.
  • Separate promised resolution from pending carrier or payment confirmation in responses.

Operational metrics

Measurement definitions, not promised improvements.

Resolution preparation time

Elapsed time from authenticated request to valid options, segmented by split-order complexity.

Refund duplication rate

Duplicate financial effects per approved refund operation, reconciled against payment records.

Promise accuracy

Audited customer commitments supported by current inventory and policy evidence divided by audited commitments.

Partial resolution backlog

Open order lines awaiting external confirmation after another line has completed.
